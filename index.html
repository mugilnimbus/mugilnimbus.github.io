Tired of clicking through the same screens, hour after hour?

Thursday

An agent that sees the screen before it acts, and one you can simply talk to.

The problem

Repetitive computer work means hours of looking, finding and clicking. An agent that helps has to see the current screen, act at exactly the right place, and stay safe when it is spoken to without a screen.

The approach

Computer control: Thursday captures the screen, a line OCR model reads every line of text and OmniParser detects every button, icon and input box with its coordinates. The LLM chooses the next action and target; a tool grounds the target to exact coordinates, acts, and the loop repeats. Voice agent: a full-duplex speech-to-speech model talks with the user on a phone and delegates real tasks to a main agent through A2A; permissions are asked and answered by voice.

Skills in practice

Computer-use agents · OCR and object detection · Grounding · Voice agents · A2A delegation

How it works

  1. The user gives Thursday a task.
  2. Thursday captures the screen or the relevant area.
  3. A line OCR model extracts every line of text.
  4. OmniParser detects every button, icon, message and input box with its coordinates.
  5. The text, the objects and the task go to the LLM, which chooses the next action and target object.
  6. A tool grounds the object to exact screen coordinates and performs the action.
  7. Thursday captures the screen again and repeats until the task is done, then replies or asks for more information.
  8. Voice agent (in progress): a speech-to-speech voice model talks with the user on a phone and delegates tasks to the main agent through A2A.
  9. Permission requests are asked by voice, and the spoken answer returns to the tool server.

Mugil’s description of Thursday, combining the earlier Thursday, Thursday V2 and Thursday V3 projects. Built independently by Mugil. The voice agent is in progress. Drawings are schematic explanations, not recordings of a live run.

Ever got an answer from AI and wondered where it came from?

Nimbus Agentic RAG

An answer with a path back to its source.

The problem

Documents are easy to collect and difficult to retrieve as useful, traceable evidence.

The approach

Full documents stay readable in SQLite. Source chunks and LLM-distilled knowledge entries have separate Qdrant collections. A bounded, read-only agent loop can search and open supporting sources.

Skills in practice

Retrieval · Qdrant / SQLite · Source attribution

How it works

  1. Keep the original document available for reading.
  2. Create semantic source chunks for fallback evidence.
  3. Distil compact knowledge entries for retrieval.
  4. Search evidence through the selected RAG path.
  5. Return an answer with inspectable sources.

Would you let an AI write to your bank balance?

Nimbus Finance

Financial truth has a clear write boundary.

The problem

AI assistance should not become the authority for balances, validation or transaction writes, and syncing a ledger should not expose its database or model engine.

The approach

The phone owns an offline-first ledger and deterministic calculations. Optional on-device or self-hosted AI uses read-only financial tools. Optional sync runs over Tailscale HTTPS to a self-hosted Kotlin/Ktor API, with PostgreSQL, encrypted backups and inference in Docker behind it.

Skills in practice

Data integrity · Android · AI boundaries · Kotlin / Ktor · Private connectivity

How it works

  1. A synthetic entry enters the financial workflow.
  2. Deterministic rules validate the entry.
  3. The ledger owns the committed financial record.
  4. A read-only tool supplies calculated information.
  5. AI explains that information outside the write boundary.
  6. Optional sync carries the ledger over private HTTPS to a self-hosted server with encrypted backups.

Public app and server documentation, and owner’s ledger-boundary description. The self-hosted server is a separate public repository, Nimbus-Finance-Server. Built independently by Mugil. No real account data or financial amounts are used in this exhibit. The sync schematic is not a deployment or network-security verification. Drawings are schematic explanations, not recordings of a live run.

Ever wondered what is actually inside a language model?

LLM View 3D

Open the model. Follow the tensors.

The problem

A checkpoint’s tensor inventory alone does not explain computation or the relationship between stored and logical shapes.

The approach

Checkpoint metadata is combined with explicit model-family definitions. A continuous 3D graph opens layers, operations and tensor bindings while preserving unresolved coverage.

Skills in practice

Model inspection · Graph reconstruction · 3D visualization

How it works

  1. Read checkpoint headers without loading weight payloads.
  2. Bind variables to explicit family definitions.
  3. Compose the text-model layer graph.
  4. Expand an operation and all required inputs.
  5. Inspect logical and stored tensor shapes.

Current public repository documentation. Built independently by Mugil. The graph is static. It does not claim measured activations or inference results; unsupported branches remain unresolved. Drawings are schematic explanations, not recordings of a live run.

Ever run out of memory just trying to shrink a model?

Model Inspection & Quantization

Make memory a first-class constraint.

The problem

Large model experiments can exhaust memory by duplicating full-precision weights during conversion or reload.

The approach

A notebook workflow inspects distributions and outliers, applies custom post-training quantization, and uses memory-aware saving and reloads. FP16 baseline outputs and timing support comparison.

Skills in practice

PyTorch · Quantization · Experimental evaluation

How it works

  1. Start with a full-precision reference.
  2. Inspect layer distributions and outliers.
  3. Apply the chosen weight representation.
  4. Save and reload through the memory-aware path.
  5. Compare against the recorded baseline under stated conditions.

Ever lost track of what your GPUs are doing mid-run?

GPU HUD

Useful telemetry in a small footprint.

The problem

Multi-GPU machines need compact resource observations that remain usable when a sensor is unavailable.

The approach

A frameless hardware monitor presents per-GPU and CPU information, configurable refresh and rolling history, with defensive handling of missing readings.

Skills in practice

Desktop software · Telemetry · Fault handling

How it works

  1. Observe available hardware sensors.
  2. Collect the selected readings.
  3. Preserve unavailable readings as missing.
  4. Maintain the configured rolling history.
  5. Present compact meters or graph views.
